# 素材：実務で実施した点と、デモで追加した点

> ワーカーへ：README の「実務で実施した点」と「デモで追加した点」は、この表だけを根拠に書きます。実務の数字は書きません（事例へのリンクで示します）。会社・製品・チーム・人の名前は書きません。デモの製品は架空の「Acme Tasks」、相手は架空の「グループ基盤」です。出典：事例 01 https://github.com/MuneAkira6/engineering-case-studies/blob/main/01-platform-integration.md

## 実務で実施した点（事例 01 に書かれていること）

| 点 | 内容 |
|---|---|
| 入口は増えても出口は一つ | 認可コード + PKCE（S256）で入り、自アプリの既存のセッションで終える。下流は変えない |
| トークンの預かり方 | 基盤のトークンはサーバー側で暗号化して預かり、自アプリのセッションを基盤のセッションにつなぐ |
| 更新の失敗の区別 | 基盤が更新を明確に拒否したら自アプリのセッションも失効、ネットワーク系の一時的なエラーでは殺さない |
| テナントの導出 | 署名済みトークンの `iss` から導き、Host ヘッダーは信用しない |
| 既存 API の Bearer 受理 | 既存トークンがないリクエストに限り受理し、メモリ上の認証主体だけを作る。セッションも DB 書き込みも作らない |
| 初回接触の一意化 | 部分ユニークインデックスと「重複キーなら読み戻す」。対照群（インデックスを外すと重複が出る）で確かめた |
| ロール | 複数クライアントの和集合 → 写像表 → 置き換え、同じなら書かない、写像できないものは一般ユーザーに降格して警告 |
| Webhook | 生バイト列で HMAC-SHA256 を検証（定数時間比較・許容 5 分）、イベント ID で一意に保存（重複は無視、30 日で失効）、先に 200 を返して非同期に処理、起動時と毎時に取り残しを回収、署名シークレットはイベントごとに分けてシークレットストアから注入 |
| テナント同期 | 排他的な claim と墓標、冪等で順不同にも安全、情報が足りなければ client_credentials で問い合わせ、「拒否」と「届かない」を区別して後者は毎時再試行・30 日で期限切れ |
| デバイス | 基盤がイベントを出さないため、テナントごとに毎時とテナント作成時に取得（ページサイズ 200）、失敗しても最終成功時刻は消さない |
| 画面の出し分け | 可視性の定義を一つのレジストリにまとめ、統合しないテナントでは最初に「隠さない」を返す。ログインへの出口を一つの認証ゲートに集め、リダイレクトのループを二段で防ぐ（一回限りのマーカーと 60 秒以内の判定） |
| 既定オフ | issuer がなければトークンはすべて拒否、署名シークレットがなければ Webhook はすべて拒否、デバイス取得は既定で false、テナント単位のフラグも既定は非統合 |
| 契約の凍結 | 並行開発の相手に、名前と形を凍結した契約を先に渡した |

## デモで追加した点

| 点 | 内容 |
|---|---|
| 基盤の代役 | IdP は Keycloak（テナントごとに realm）、イベント・テナント API・デバイス API はモック。実務の基盤の挙動は再現せず、事例に書いた設計を確かめるための代役 |
| SDD → goal 包 → バス | この仕様（`specs/001-…`）の受け入れ条件から goal 包を作り、goal-bus-kit のバスで無人実装した。実務では SDD とバスは別々に使っていた |
| 時計の注入 | 実務では毎時のタイマーを実際に 69 分待って確かめた。デモでは注入できる時計でテストを進め、そのことをテストに書く（本番の間隔は実際の値のまま） |
| モックの操作 API | 署名の誤り・古いタイムスタンプ・再送・テナント API の拒否や不達をテストから起こすための `/__control/*` |
| 一つの Compose | Keycloak と MongoDB を一つの Compose で起動し、Node のサービスはワークスペースから直接動かす |
